# API-DOCS-01 — Route Inventory

**Initiative:** API-DOCS-01 — OpenAPI and Swagger

**Inventory date:** 2026-07-30

**Status:** Planning evidence; no runtime or documentation implementation is performed here.

## Scope and evidence rules

This inventory is a repository-grounded input to the initial OpenAPI contract. It covers:

1. every project-owned `apps/backend/src/api/**/route.ts` file;
2. every HTTP method exported by those files;
3. native Medusa operations whose behavior is changed by project middleware in `apps/backend/src/api/middlewares.ts`;
4. route-local validators, serializers, query configuration, modules/workflows, and HTTP or unit tests that materially define each contract.

Paths use OpenAPI parameter notation (`{id}`) even when the source uses Medusa file parameters (`[id]`) or middleware parameters (`:id`). “Initial” in the **Documentar** column is a proposal for API-DOCS-01, not evidence that an OpenAPI operation already exists. “Try it out” is also a documentation-safety proposal, not a claim about current Swagger configuration.

The inventory does not infer exact endpoints from product requirements alone. An operation appears below only when a project route handler exists or project middleware concretely extends a native Medusa handler. Native schemas are named only where the installed Medusa source confirms the validator or response envelope.

All `/store/*` operations require the Medusa publishable API key header and permit optional customer bearer/session identity by framework default. Route middleware makes customer identity mandatory only where stated. All `/admin/*` operations use Medusa Admin authentication; the refund, exchange, and operational-alert custom handlers additionally require an authenticated `user` actor and reject API-key actors. Framework evidence is in `node_modules/@medusajs/framework/dist/http/router.js:86-102` and `node_modules/@medusajs/framework/dist/http/middlewares/ensure-publishable-api-key.js:5-56`; the stricter custom Admin rule is in `apps/backend/src/api/admin/_shared/require-admin-actor.ts:34-75`.

Every operation also traverses the project correlation/access-log middleware and returns `x-correlation-id`; unhandled errors traverse the project Sentry error middleware (`apps/backend/src/api/middlewares.ts:220-270`).

## Native Medusa extension boundary

The six native operations are included because project middleware changes their observable contract:

- `GET /store/products` and `GET /store/products/{id}` force a stable public field set, remove unsellable catalog records, normalize BRL prices, and expose project-owned storefront serializers.
- `POST /admin/products`, `POST /admin/products/{id}`, `POST /admin/products/{id}/variants`, and `POST /admin/products/{id}/variants/{variant_id}` add the project sellable-product gate before the installed Medusa handler executes.

No native Medusa route is replaced by a local `route.ts`. Therefore the inventory deliberately uses **Native Medusa extension**, not **Native Medusa override**, for all six operations.

The future storefront requirements mention additional native commerce capabilities, but the repository does not yet pin an exact allowlist of unmodified native methods and paths for those capabilities. They are not counted as discovered operations and are not silently added to the initial contract. A later implementation wave must select them explicitly from the installed Medusa route set before generating OpenAPI for them.

## Explicit exclusions

1. `GET /store/custom` — excluded because it is a scaffold/example handler with an empty success response and no business contract or operation-specific test.
2. `GET /admin/custom` — excluded for the same reason.

The following are boundary findings, not additional excluded HTTP operations:

- **Admin — Audit:** no project AdminActionLog read/list HTTP handler exists. Audit writes support refund and exchange actions, and the reconciliation job is worker-only; neither is an undocumented HTTP route.
- **Internal:** no project `/internal` `route.ts` exists.
- **Customer exchange self-service:** no Store route exists; the current exchange flow is Admin-only.
- **Unmodified native Medusa routes:** not counted merely because they are installed. Only the six concretely extended native operations enter this evidence set.

## Documentation safety and implementation notes

- Never enable interactive execution for payment initiation, cart/customer mutations, Admin mutations, tracking lookup, operational alert reads against production, or webhook callbacks.
- Store documentation must model `x-publishable-api-key` independently from optional/required customer bearer or session identity.
- Sensitive custom Admin routes must not advertise Admin API-key actors as sufficient; their route-level `user` actor check is stricter than the namespace default.
- Webhook examples must be synthetic and must not contain real signatures, secrets, raw customer payloads, addresses, or provider identifiers.
- The tracking token belongs only in the request body, never in a path/query example. Plaintext exposure is one-time at issuance, while lookup use is repeatable until expiry/revocation and updates `last_used_at`. Error documentation must preserve the indistinguishable invalid-token behavior.
- Monetary units are an explicit boundary: Cart and PaymentSession values are BRL major units; PaymentAttempt and refund request/availability amounts are integer BRL minor units. Payment-attempt examples must not accept client-authored money fields, and refund examples must not pass a major-unit amount without conversion.
- Native schema references must remain version-aligned with the installed Medusa packages. The project-owned serializers and gates are the local deltas that API-DOCS-01 must preserve.
