## Reset failure/retry protocol — P14-D09

O endpoint `POST /auth/customer/emailpass/update` consome obrigatoriamente o protocolo `reset-confirm` aprovado em 14-08. Antes de qualquer lookup, claim, consumo de token, provider ou write, aplica 30/IP/15 min e 10/(IP,presented reset token)/15 min com as keys HMAC domain-separated/versionadas definidas naquele plano. Somente depois de encontrar uma intent legítima aplica 10/(IP,reset-intent)/15 min; malformed semantic capability, intent ausente ou token desconhecido percorrem o post dummy derivado do pre-digest com o mesmo número de operações Redis, dummy work, HTTP e timing, sem account dependence. Threshold excedido encerra com `429 RATE_LIMITED`; Redis indisponível encerra com `503 AUTH_TEMPORARILY_UNAVAILABLE` e `Retry-After: 60`, sempre antes de lookup/claim/consumo/provider/mutação. IP/token/intent puros, hash persistido e `newPassword` nunca entram em key/log/telemetry; `newPassword` permanece somente na memória do request, sem persistência ou fingerprint.

As provas do plano 14-08 são obrigatórias neste slice: `missing|malformed semantic capability|expired|used|superseded` compartilham `400 RESET_INVALID_OR_EXPIRED` com headers/body equivalentes; o caminho valid-invalid-password-provider, quando aplicável, participa da matriz de 40 amostras; floor 350 ms, jitter CSPRNG 0..50 ms, delta de mediana <=50 ms e p95 <=75 ms. `AUTH_RECOVERY_PENDING` não substitui outage/invalid: ele é exclusivo de uma intent legítima já correlacionada à mesma operation e `Idempotency-Key`, em estado composto ambíguo/reconciliável desta state machine.

Pre-call transaction: lock intent; validate hash/pending/expiry; bind `operation_id` to HMAC da `Idempotency-Key`; record `credential_version_before` and target `credential_version_before+1`; transition intent/recovery to `claimed`; token becomes unavailable to any other operation. No password, derived password fingerprint or capability is persisted.

Provider call: update to the request's `newPassword`. A definitive success is followed, within the same request, by read-only emailpass verification of that exact in-memory password. Only successful verification correlated to the claimed operation/CAS target is `provider_password_proof`; then persist `credential_updated_at`/proof reason (never the secret), increment credential version, revoke all lineages with the same operation id, mark `revocation_committed`, consume the intent and mark completed.

Timeout/ambiguous: do not set `credential_updated_at`; set `provider_outcome_ambiguous|failed_reconcilable`, keep identity fail-closed and return 503. The secretless reconciler may claim/renew lease, ensure all lineages are revoked, retain block, retry non-secret DB transitions and emit sanitized alert; it cannot call password verify/update, infer provider result, consume token, mark credential_updated/completed or return success. Retry requires the same `Idempotency-Key` and `newPassword` reapresentada. It first verifies the presented value against provider: success supplies the missing proof; failure permits one provider update for that same retry followed by mandatory verification; another timeout remains pending. Different key cannot take over. The contract requires the caller to re-present the intended password; the backend deliberately stores no comparable password fingerprint.
