## Password-change failure/retry protocol — D14-16

Initial request: stable access guard + currentPassword provider proof; then transaction binds HMAC(Idempotency-Key), records `current_password_verified_at`, version-before/target and `change_claimed`; all ordinary access/login/refresh becomes fail-closed. Provider update/mandatory read-only verification of in-memory newPassword follows the reset proof protocol. Definitive proof authorizes credential version bump, all-lineage revoke and 204.

Timeout/ambiguous: no credential_updated marker; return 503 and keep block. Rotina secretless pode no máximo revogar lineages/renovar lease/alertar, nunca verificar/atualizar password, inventar proof ou completar. Since the original access token is now blocked, only this route may use a resume-only guard: cryptographically valid original token + same identity/customer + same operation key hash + same `Idempotency-Key`; it cannot authorize any other handler. Retry must re-present `newPassword`; successful provider verification supplies proof, otherwise one update+verify attempt is allowed. CurrentPassword proof from the claimed operation remains bound; different key/new operation is rejected. No password/fingerprint/capability is persisted.
