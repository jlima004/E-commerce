## Replay contract (B15-P-HR-02 / P15-D09)

- Mint success = HTTP **201** with `x-indicio-guest-cart-token` (guest create only).
- Replay of the same Idempotency-Key = HTTP **200**.
- `StoreIdempotencyRecord` stores allowlisted pointers only (`operation`, `result_id` = cart_id, `response_status`). It does **not** persist a full response DTO, ETag string, or capability.
- Replay algorithm: read `result_id`/`cart_id` → refetch current canonical cart → serialize `PublicStoreCartPreOrder` → read current `StoreResourceVersion` → respond 200 + current ETag. NEVER re-emit capability.
- Prove refetch: mutate cart (or version) between 201 and replay and assert the replay body matches **current** canonical state, not the 201 snapshot.
- Q-11 Option A: after perda B, orphan remains inaccessible without the original secret; a **new** Idempotency-Key creates a new cart.

POST active does **not** require If-Match (not a structural mutation). Line-item If-Match lands in 15-05.

Claim lifecycle uses existing store-idempotency states only: `processing`, `completed`, `failed_retryable`, `failed_terminal`, `reconciliation_required`, `reconciliation_unresolved`. Success → `markCompleted`. Retryable failure → `markFailedRetryable`. Terminal failure → `markFailedTerminal`. Do not invent a new state machine.

Execution subagent policy: see 15-01 `Phase 15 Execution Orchestration Policy`. This PLAN does not authorize EXECUTION.

## Partial-effect create→mint (B15-P-RP-HR-03)

Sequence that must be specified, not assumed atomic:

`claim` → `createCartWorkflow` COMMIT → mint/persist capability FAIL

This state **must not** become a blind retry of create.

**Before any persisted side effect:** a technically retryable failure MAY use `markFailedRetryable`.

**After cart creation is confirmed:**

- same Idempotency-Key MUST NOT blindly execute another create;
- preserve `result_id`/`cart_id` when possible;
- capability plaintext remains irrecoverable;
- do not persist, reconstruct, or re-emit capability;
- classify using **only** the existing store-idempotency states listed above.

If the create effect is confirmed and mint/persist of capability fails:

- record the known effect (`result_id`/`cart_id`) when supported;
- use `reconciliation_required` if the record needs reconciliation, **or** `failed_terminal` when the outcome is definitely terminal;
- never `failed_retryable` if that would allow a second create (`failed_retryable` → `processing` is an existing allowed transition);
- retry of the same key must return/forward the already-recorded condition, never create a new cart.

If, during EXECUTION, it is proven that create cart + persist capability can share a truly atomic PostgreSQL transaction, that alternative MAY be adopted. This PLAN must **not** assume atomicity without as-built proof.

Q-11 Option A remains locked (P15-D09): orphan after perda B; replay of the same key does not re-emit capability; a new key creates a new cart.
