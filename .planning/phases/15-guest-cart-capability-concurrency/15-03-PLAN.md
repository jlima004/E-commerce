## Active M1 contract (B15-P-HR-01 / B15-P-HR-04)

GET `/store/carts/active`:

- valid guest capability → guest cart 200
- missing capability + no valid Customer context → 404
- presented invalid / expired / revoked / consumed capability → uniform 404
- valid Phase-14 Customer context → customer active cart

POST `/store/carts/active`:

- no capability + guest/BFF → create guest cart (201)
- valid capability → reuse guest cart (no re-emit)
- capability PRESENT but invalid/terminal → uniform 404; MUST NOT silently create a new cart
- valid Phase-14 Customer context → create/reuse Customer cart; no guest capability emitted

XOR: if the guest capability header is present, resolve guest lookup; invalid/terminal → 404; do not fall through to Customer. Customer path requires BFF + Phase-14 `customerAuthAccessGuard` `customerId`. Native `authenticate("customer", ["session", "bearer"])`, raw JWT, JWT hash and Medusa session id are not M1 proof.

Execution subagent policy: see 15-01 `Phase 15 Execution Orchestration Policy`. This PLAN does not authorize EXECUTION.

### Mixed Guest+Customer middleware (B15-P-RP-HR-01)

`GET`/`POST` `/store/carts/active` is a mixed Guest + Customer surface. The six cart operations in `STORE_CART_BFF_PROTECTED_OPERATIONS` are mixed the same way once promoted.

Matcher stack for `/store/carts/active`:

1. Store surface authority
2. BFF service guard (`customerAuthBffServiceGuardMiddleware`)
3. Conditional actor resolution (`resolveM1CartActor` or equivalent)
4. Handler

Keep existing `storeCartPreOrder` query/response middlewares. They are serialization/query helpers, not actor authority.

Do **not** mount raw `customerAuthAccessGuardMiddleware` unconditionally on the matcher for `/store/carts/active` or the other mixed cart routes. Guest requests have no Customer `Authorization` and would die before the handler.

Actor resolution (mandatory):

- **A) capability header PRESENT** → Guest lookup. Valid → Guest. Invalid / expired / revoked / consumed → uniform 404. **Never** fall through to Customer.
- **B) capability ABSENT + `Authorization` PRESENT** → execute the Phase-14 approved Customer authority (`customerAuthAccessGuard` / PostgreSQL-backed access state) → stable `customerId` → Customer. Do not invent a second Customer authority.
- **C) capability ABSENT + `Authorization` ABSENT** → GET 404; POST Guest create allowed with BFF.

Future implementation MAY call that **same** Phase-14 access authority conditionally inside the actor resolver, or use a wrapper middleware that invokes the access guard only when `Authorization` is present. Native Medusa session/bearer is not M1 possession. Raw JWT / JWT hash / Medusa session id are not actor scope. Presented Guest capability has precedence and fails closed. Customer active remains in the same cut as Guest active.

Staged manifest after this plan (P15-D06 parcial): total 63, native identity 51, local 12, EXTENDED 15, DENY 50, PRESERVE_LEGACY 5, M1_ENABLED 8. `STORE_SURFACE_PHASE14_ENABLED_OPERATIONS` remains the Auth six. `STORE_SURFACE_PHASE15_CART_ENABLED_OPERATIONS` begins with GET/POST active.

BFF matchers for the four line-item operations may be registered now (tuple of six) while those handlers remain DENY. Surface guard DENY stays authoritative until 15-05/15-06.

ETag / StoreResourceVersion wiring is **15-04**. Tracer may document ETag as optional/absent. Do not invent a fake ETag.

Idempotency complete wiring is **15-04**. This plan may mint on first guest 201; it must not treat replay as stored DTO and must not re-emit the capability on GET.
