# Phase 12.1 — Validation Strategy

## Purpose

Este contrato mapeia os 18 closure criteria para planos, tarefas, superfícies, classes de evidência, sanitização e decisões PASS/BLOCKED. Ele não autoriza execução nem declara resultado.

## Evidence classes

Cada item futuro usa exatamente uma classe:

- `local process`
- `local PostgreSQL disposable`
- `Heroku release`
- `production read-only`
- `production mutation`
- `real external provider`
- `inferred only`

Inferência e evidência histórica nunca são promovidas a execução atual.

## Release identity contract (P12_RELEASE_CONTRACT_V1)

Nomenclatura única para C05/C12/C16/C17, exigida de forma idêntica nos SUMMARYs de 12.1-02, 12.1-03 e 12.1-06:

- `predeploy_current_release`: release Heroku ativa imediatamente antes do deploy autorizado do 12.1-03; é o rollback target primário e único.
- `previous_eligible_release`: candidata elegível anterior à `predeploy_current_release`; evidência histórica apenas — nunca substitui automaticamente o rollback target se a primária se tornar inelegível.
- `deployed_release` / `candidate_sha`: release criada pelo deploy autorizado do 12.1-03 via refspec `$P12_CANDIDATE_SHA`:refs/heads/main` e o SHA completo testado no 12.1-01 (`execution_base_sha` propagado pelo 12.1-02).
- `rollback_target_sha`: SHA completo da release `predeploy_current_release` para a qual um rollback documentado apontaria; se o rollback target se tornar inelegível, o resultado é `BLOCKED` com nova decisão humana e novo preflight — nenhuma substituição aproximada por `previous_eligible_release` é permitida.
- `documentary_head`: HEAD Git no momento do deploy; pode ser descendente allowlisted do `candidate_sha` somente por commits dos SUMMARYs 01/02; nunca é promovido a release SHA.

C17 exige compatibilidade SHA-based entre `rollback_target_sha` e `candidate_sha` (schema/migration compatibility) e cross-check de que os três SUMMARYs (12.1-02, 12.1-03, 12.1-06) usam os mesmos IDs/SHA para cada papel. C05 exige `deployed_sha == candidate_sha` e proíbe deploy do HEAD documental. Qualquer divergência de nomenclatura ou de valor entre os três SUMMARYs bloqueia C17.

### Disposable schema manifests (Prova D / C03)

O child Node/`pg` da Prova D de 12.1-01 T2 deve incorporar estes manifests como
arrays literais. Source class inventory e mappings vêm de leitura local do
source (`local process`); history/tables/constraints/indexes vêm do lifecycle
PostgreSQL descartável próprio, separado das cinco specs da Prova B. Queries de
catálogo ficam limitadas às 11 tabelas abaixo.

Query obrigatória de constraints (somente as 11 tabelas):

```sql
select
  c.conname,
  c.contype,
  t.relname as table_name,
  pg_get_constraintdef(c.oid, true) as definition
from pg_catalog.pg_constraint c
join pg_catalog.pg_class t
  on t.oid = c.conrelid
join pg_catalog.pg_namespace n
  on n.oid = t.relnamespace
where n.nspname = 'public'
  and t.relname = any($1)
```

Modelo de constraints (três buckets — os 33 nomes estáveis NÃO são o conjunto
total de `pg_constraint`):

```text
A. Stable named constraints — 33/33 semantic exact
B. Generated semantic constraints — 28/28 semantic exact multiset
C. Unexpected constraints — must be 0
```

Cada linha de `pg_constraint` nas 11 tabelas entra em exatamente um bucket.
Uma constraint não pode satisfazer A e B simultaneamente. Duplicate consumption
ou linha não consumida → `BLOCKED`.

**Bucket A** exige por linha: `conname` allowlisted entre os 33; `table` exact;
`contype` exact; semantic ID exact; multiplicity 1. Nome correto com definição
semântica incorreta → `BLOCKED`. Presença-only não é PASS.

**Bucket B** exige por linha: `conname` não é identidade; `table` exact;
`contype = c`; semantic ID ∈ allowlist dos 28; multiplicity exact (1 cada).
`conname` gerado pelo PostgreSQL nunca é identidade.

**Bucket C:** qualquer linha não consumida exatamente uma vez.

Persistência permitida: nomes estáveis; stable semantic IDs; generated semantic
IDs; contagens; tabelas allowlisted; tipos de constraint;
missing/extra counts. Para unexpected somente `unexpected_constraint_count`,
tabela allowlisted afetada e `constraint type`. Proibido persistir: unexpected
`conname`; definição inesperada completa; schema dump; saída bruta de
`pg_get_constraintdef`; dados de negócio; credential URL.

### Semantic ID contract (closed)

IDs fechados, independentes da formatação de `pg_get_constraintdef`:

```text
pkey:<table>:[<ordered-columns>]
unique:<table>:[<ordered-columns>]
check:<table>:<semantic-rule>
```

Exemplos:

```text
pkey:payment_attempt:[id]
unique:operational_alert:[type,entity_type,entity_id]
check:operational_alert:type:in:[payment_stuck,fulfillment_failed]
```

### PRIMARY KEY and UNIQUE column verification

Para `contype IN ('p', 'u')`, o audit futuro não depende apenas de
`pg_get_constraintdef`. Exigir query de colunas ordenadas:

```sql
select
  c.conname,
  c.contype,
  t.relname as table_name,
  array_agg(a.attname order by cols.ord) as column_names
from pg_catalog.pg_constraint c
join pg_catalog.pg_class t on t.oid = c.conrelid
join pg_catalog.pg_namespace n on n.oid = t.relnamespace
cross join lateral unnest(c.conkey) WITH ORDINALITY as cols(attnum, ord)
join pg_catalog.pg_attribute a
  on a.attrelid = c.conrelid and a.attnum = cols.attnum
where n.nspname = 'public'
  and t.relname = any($1)
  and c.contype in ('p', 'u')
group by c.conname, c.contype, t.relname, c.oid
```

A ordem de `conkey` deve ser preservada. Não ordenar alfabeticamente.
Resultado canônico: `pkey:<table>:[col1,col2,...]` ou
`unique:<table>:[col1,col2,...]`. Para PKs estáveis, exigir colunas exatamente
`[id]` na ordem exact.

### CHECK canonicalization pipeline (fail-closed)

Para cada constraint `contype = 'c'`:

1. receber `table_name`, `conname` e `pg_get_constraintdef(oid, true)`;
2. remover somente o wrapper externo `CHECK (...)`;
3. tokenizar a expressão;
4. normalizar identificadores quoted/unquoted para o nome esperado;
5. normalizar literais SQL;
6. remover somente casts allowlisted;
7. reconhecer uma das formas semânticas fechadas abaixo;
8. produzir exatamente um semantic ID;
9. bloquear em ambiguidade ou sobra de tokens.

Proibido: avaliação dinâmica; `eval`; SQL derivado da definição; comparação
direta de strings brutas de `pg_get_constraintdef`; simplificação booleana
genérica; equivalência de expressões arbitrárias.

**Casts allowlisted** (remover apenas quando produzidos pelo PostgreSQL e
compatíveis com o manifest): `::text`, `::text[]`, `::integer`, `::bigint`,
`::jsonb`, e forma funcional equivalente na decompilação. Qualquer outro cast →
`BLOCKED`.

**Formas semânticas permitidas:**

| Forma | Equivalentes reconhecidos | Semantic ID |
|---|---|---|
| Membership | `column IN ('a','b')` ≡ `column = ANY (ARRAY['a','b'])` | `check:<table>:<column>:in:[a,b]` (ordem preservada; sem duplicatas/extras; rejeitar NOT IN, ALL, subquery, coluna diferente) |
| Singleton membership | `column IN ('a')` ≡ `column = ANY (ARRAY['a'])` ≡ `column = 'a'` | `check:<table>:<column>:in:[a]` (somente quando manifest espera um valor) |
| Comparações numéricas | `>`, `>=`, `=`, `<=` | `check:<table>:<column>:gt:N`, `:gte:N`, `:eq:N`, `:lte:N` |
| Nullable membership | `column IS NULL OR column IN (...)` ≡ `... = ANY (ARRAY[...])` | `check:<table>:<column>:nullable-in:[...]` |
| Comprimento btrim | `length(btrim(column)) BETWEEN min AND max` | `check:<table>:<column>:btrim-length-between:min:max` (não aceitar `length(column)`) |
| Comprimento nullable | `column IS NULL OR length(column) <= max` | `check:<table>:<column>:nullable-length-lte:max` |
| JSONB object nullable | `column IS NULL OR jsonb_typeof(column) = 'object'` | `check:<table>:<column>:nullable-jsonb-type:object` |
| Implicação intent/result | `audit_stage <> 'intent' OR result = 'requested'` | `check:admin_action_log:intent-result:if-audit-stage-intent-then-result-requested` |

Qualquer forma não reconhecida → `BLOCKED`.
