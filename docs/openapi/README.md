# OpenAPI contract maintenance

This repository owns exactly three OpenAPI `3.1.2` documents:

| Surface  | Generated artifact                                          | Runtime endpoint         |
| -------- | ----------------------------------------------------------- | ------------------------ |
| Store    | `apps/backend/src/api-docs/generated/store.openapi.json`    | `/openapi/store.json`    |
| Admin    | `apps/backend/src/api-docs/generated/admin.openapi.json`    | `/openapi/admin.json`    |
| Webhooks | `apps/backend/src/api-docs/generated/webhooks.openapi.json` | `/openapi/webhooks.json` |

The TypeScript registry below `apps/backend/src/api-docs/` is the source of
truth. Generated files are deterministic, committed artifacts; they are never
edited manually and are never generated by the web or worker process.

## Contract boundaries

- Store contains shopper-facing custom routes, the selected native Store
  extensions, and health endpoints.
- Admin contains operator routes and the selected native Admin extensions.
- Webhooks contains only Stripe and Gelato ingress contracts.
- Shared components may be reused only when they do not pull an internal schema
  into Store. Every `$ref` is local to its self-contained document.
- Every operation requires globally unique `operationId`, tags, summary,
  security, responses, provenance, inclusion reason and non-interactive status.

Route discovery is a coverage input, not a semantic generator. A project route
must be registered or listed in `coverage/exclusions.ts` with source, reason,
owner and review trigger. Native behavior modified by the project belongs in
the six-entry, versioned manifest in `coverage/native-routes.ts`; a Medusa or
evidence-file change requires review and an explicit fingerprint update.

## Schemas and examples

Reuse a Zod schema only when that same schema governs runtime behavior and its
input/output shapes are identical for the documented position. Transforms,
coercions, defaults, stripping or response enrichment require separately named
request/response schemas or explicit OpenAPI schemas backed by contract tests.

Examples are optional and synthetic. Omit them when realistic content would
require credentials, signatures, API keys, Stripe client secrets, Pix payloads,
tracking tokens, provider production identifiers, personal documents, email,
phone or address data. The registry and global checker reject these classes.

## Contributor workflow

1. Update the operation, schema and evidence in the correct surface.
2. Run the scoped read-only verifier:

   ```bash
   npm run openapi:verify:store
   npm run openapi:verify:admin
   npm run openapi:verify:webhooks
   ```

3. Run `npm run openapi:lint`.
4. If bytes must change, run exactly one explicit writer and review the diff:

   ```bash
   npm run openapi:generate -- --surface store
   # or: admin, webhooks, all
   ```

5. Commit the reviewed artifact. From a clean checkout, run
   `npm run openapi:check`. This global command is read-only, rebuilds twice in
   memory, compares byte-for-byte with the three tracked artifacts, and checks
   global coverage, metadata, security and native fingerprints.

Never run the writer immediately before or from inside the global drift gate.
If `openapi:check` reports drift, stop, regenerate in an implementation
workspace, review and commit the result, then restart the clean gate.

## Toolchain and CI

- Generator: `@asteasolutions/zod-to-openapi@9.1.0`.
- Linter: local `@stoplight/spectral-cli@6.16.2`, root `.spectral.yaml`, local
  `spectral:oas`, `--fail-severity warn`; no remote ruleset or ignore file.
- UI assets: runtime `swagger-ui-dist@5.32.11`.
- Install with `SCARF_ANALYTICS=false npm ci`; root
  `scarfSettings.enabled=false` is mandatory.

`.github/workflows/api-docs.yml` runs the clean global check before any writer,
then lint, focused contracts, HTTP exposure, repository lint, build, packaged
artifact/asset checks and clean-worktree assertions.

## Runtime policy

Swagger UI uses only same-origin local assets, `validatorUrl: null`,
`persistAuthorization: false`, `queryConfigEnabled: false`,
`withCredentials: false` and immutable `supportedSubmitMethods: []`. Production
exposure is disabled by default and requires a separate human operational gate.
See `ops/API_DOCS.md`; this document does not authorize production enablement.
